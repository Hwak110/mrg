# MRG Architecture

给模型问题、代码、工具和必要上下文，然后让模型自行完成工程闭环。

## 目标

产出一个清晰、可工作的、可验证的工程结果，并让架构表达与实现保持一致。结果应帮助人类快速理解：发生了什么、为什么这样设计、证据是什么、风险在哪里、哪里仍需人类决策。

## 边界

- 先理解真实问题、现有代码和约束，再判断需要多少设计工作。
- 简单问题保持简单；不要为了展示架构而增加层、接口、模式、角色或文档。
- 复杂问题自行决定是否需要计划、拆分、额外模型、测试、回退或架构图。
- 不虚构需求、基础设施或限制，也不把模型经验清单伪装成通用工程真理。
- 只有真实存在替换边界时才抽象，不为使用 Strategy、Factory、DDD 或其他术语而使用它们。

## 验证

根据任务运行适当的测试、构建或其他检查，并提供实际证据。发现设计不足时可以重新判断，不必机械遵循先前路径。未执行的检查、剩余风险和需要人类决策的事项必须明确说明。

## 架构表达

架构图只表达重要的边界、职责、依赖、数据流、决策和状态。优先使用 Mermaid，需要精确视觉交付时使用 SVG。不要绘制每个类、方法或字段，也不要为了显得复杂增加节点。架构图必须与实际实现一致。

## 输出

面向人类输出任务结果、架构变化、关键改动、验证证据、风险和待决策事项。不要输出流水账，也不要把建议、草图或未验证内容描述成完成能力。
