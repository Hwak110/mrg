# MRG Architecture

给模型问题、代码、工具和必要上下文，然后让模型自行选择完成工作的路径。

## 核心原则

- 先理解真实问题、现有代码和约束，再决定是否需要架构设计。
- 目标是最简单、清晰、可演进且能自然落到代码的结构，不是套用模式。
- 优先复用现有系统，不为“架构完整”增加没有实际价值的层、接口、流程或依赖。
- 简单问题保持简单；如果只需修改 DTO、映射或测试，就直接完成，不强行引入复杂架构。
- 不虚构不存在的需求、约束、基础设施或业务规则。

## 工作范围

根据任务自行判断是否需要阅读更多代码、形成方案、拆分模块、运行测试、创建架构图或询问人类。不要把这些动作当成固定流程。

## 架构与实现

需要架构判断时，说明问题与目标、核心设计、模块职责和依赖、关键数据流与失败路径、关键取舍，以及如何自然落到 Java 或现有技术栈。

只有真实存在替换边界时才抽象；不要为了使用 Strategy、Factory、DDD、Clean Architecture 或其他术语而使用它们。

## 实现与验证

遵循现有项目约定，保持改动范围与问题匹配。运行与改动最相关的测试、构建或检查；未执行的检查明确说明。发现原设计不足时可以回到架构判断，不必机械遵循先前方案。

## 架构图

架构图是帮助人理解系统的视图，只表达重要的系统边界、模块职责、依赖关系、核心数据流、关键决策和状态。优先使用 Mermaid；需要精确视觉交付时可使用 SVG。不要绘制每个类、方法或字段，不为显得复杂而增加节点。图必须与实际实现保持一致。

## 输出

完成后说明实际修改、验证结果、重要取舍、假设和剩余风险。不要把建议、草图或未验证内容描述成已完成能力。
